# RBAC implementation plan

## Goal
Implement consistent role-based access for `SUPER_ADMIN`, `MANAGER`, and `STAFF` across the admin panel so route access, sidebar visibility, dashboard data, server actions, and APIs all enforce the same rules.

## Confirmed product decisions
- `SUPER_ADMIN`: full access, including `Users` and sensitive `Settings`
- `MANAGER`: business and operations management, but no `Users`
- `STAFF`: operational-only access
- `STAFF` can view `Purchases` but cannot update payment status
- `STAFF` can manage voucher operational actions like redeem/extend/void

## Recommended approach
Use `public.admins.role` as the single source of truth for authorization. Treat `auth.users.user_metadata.role` as a temporary mirror for compatibility only during rollout.

## Implementation steps

### 1. Centralize role and permission logic
Create a shared RBAC helper module to normalize roles, resolve the current admin record, and check permissions.

Files:
- `lib/auth/admin-rbac.ts` (new)
- `lib/types.ts`
- `context/AuthContext.tsx`

Plan:
- Define canonical roles: `SUPER_ADMIN`, `MANAGER`, `STAFF`
- Add permission constants by capability, not by page, for example:
  - `dashboard.view_operational`
  - `dashboard.view_business`
  - `orders.view`
  - `orders.update_payment_status`
  - `vouchers.manage`
  - `services.manage`
  - `reviews.manage`
  - `users.manage`
  - `settings.manage_sensitive`
- Add helpers such as:
  - `normalizeAdminRole()`
  - `getCurrentAdminAccess()`
  - `hasPermission()`
  - `requirePermission()`
  - `canAccessAdminRoute()`
- Stop defaulting missing roles to `STAFF` in `context/AuthContext.tsx`; missing/unknown role should be unauthorized
- Keep a temporary compatibility mapping from legacy `ADMIN` to `MANAGER`

### 2. Harden server-side authorization first
Apply permission checks in trusted server paths before touching UI so hidden buttons are not the only protection.

Files:
- `lib/actions/admin-users.ts`
- `lib/actions/services.ts`
- `lib/actions/vouchers.ts`
- `lib/actions/orders.ts`
- `lib/actions/reviews.ts`
- `app/api/orders/[id]/status/route.ts`

Plan:
- Require `users.manage` for admin user create/update
- Require `services.manage` for service create/update/delete
- Require `vouchers.manage` for voucher redeem/extend/void
- Require `orders.view` for admin order reads
- Require `orders.update_payment_status` for manual payment status changes
- Require `reviews.manage` for review deletion/moderation
- Update the order status API to enforce manager-or-super-admin access explicitly
- Return `403` for unauthorized calls and log actor id/role for sensitive mutations

### 3. Enforce route-level access in admin pages
Add page-level server guards so direct URL access is blocked even if a user manually enters a route.

Files:
- `app/admin/layout.tsx`
- `app/admin/dashboard/page.tsx`
- `app/admin/purchases/page.tsx`
- `app/admin/vouchers/page.tsx`
- `app/admin/services/page.tsx`
- `app/admin/reviews/page.tsx`
- `app/admin/users/page.tsx`
- `app/admin/settings/page.tsx`

Plan:
- Keep middleware for coarse session protection only
- Add authoritative route checks inside server components/layout using the shared RBAC helper
- Redirect unauthorized users to `/admin/dashboard` or a `403` admin state
- Route matrix:
  - `Dashboard`: `SUPER_ADMIN`, `MANAGER`, `STAFF`
  - `Purchases`: `SUPER_ADMIN`, `MANAGER`, `STAFF` (view only for staff)
  - `Vouchers`: `SUPER_ADMIN`, `MANAGER`, `STAFF`
  - `Services`: `SUPER_ADMIN`, `MANAGER`
  - `Reviews`: `SUPER_ADMIN`, `MANAGER`
  - `Users`: `SUPER_ADMIN` only
  - `Settings`: `SUPER_ADMIN` only

### 4. Scope sidebar and client actions by permission
Make the UI reflect the same permission model so users only see routes and actions they can actually use.

Files:
- `components/admin/sidebar.tsx`
- `components/admin/dashboard-client.tsx`
- `components/admin/purchases-client.tsx`
- `components/admin/vouchers-client.tsx`
- `components/admin/services-client.tsx`
- `components/admin/reviews-client.tsx`
- `components/admin/admin-users-client.tsx`
- `components/admin/settings-client.tsx`
- `components/admin/dashboard-header.tsx`

Plan:
- Replace the static sidebar nav list with a permission-aware nav config
- Hide `Users`, `Settings`, `Services`, and `Reviews` from `STAFF`
- Hide `Users` from `MANAGER`
- Disable or remove purchase status update controls for `STAFF`
- Keep voucher operational actions available to `STAFF`
- Guard destructive or sensitive buttons in the client, but rely on server checks for real enforcement

### 5. Split dashboard by role and avoid overfetching
Show different dashboard widgets per role and do not fetch sensitive aggregates for staff.

Files:
- `lib/actions/dashboard.ts`
- `components/admin/dashboard-client.tsx`
- `components/admin/chart-card.tsx`
- `components/admin/recent-orders.tsx`
- `components/admin/voucher-summary.tsx`

Plan:
- Create permission-aware dashboard data loading
- `STAFF` dashboard: operational widgets only
  - active vouchers
  - redeemed vouchers
  - recent orders read-only
  - voucher summary / operational activity
- `MANAGER` dashboard: add business widgets
  - total revenue
  - revenue chart
  - review metrics
  - service totals
- `SUPER_ADMIN` dashboard: same as manager plus any future admin/system-only widgets
- Do not compute or return revenue/business-only data for `STAFF`

### 6. Align auth metadata with database role model
Clean up the legacy mismatch so runtime auth and database authorization stop drifting apart.

Files:
- `lib/supabase/middleware.ts`
- `context/AuthContext.tsx`
- `lib/actions/admin-users.ts`
- relevant Supabase migration under `lib/supabase/migrations/`

Plan:
- Update middleware so it no longer trusts metadata alone for authorization decisions
- Make admin user create/update keep `auth.users.user_metadata.role` synchronized with `public.admins.role`
- Add a migration or one-time sync script to:
  - map legacy `ADMIN` to `MANAGER`
  - identify auth users missing `public.admins` rows
  - identify role mismatches between auth metadata and `public.admins`
- Remove `ADMIN` from app types after compatibility cleanup is done

## Verification

### Type and lint
- `bunx tsc --noEmit`
- `bun run lint`

### Manual role matrix
Test with one account per role plus one unauthorized account.

- `SUPER_ADMIN`
  - can access all admin routes
  - can manage users and settings
  - can update purchase payment status
- `MANAGER`
  - can access dashboard, services, purchases, reviews, vouchers
  - cannot access `Users`
  - cannot access sensitive settings
  - can update purchase payment status
- `STAFF`
  - can access dashboard, purchases, vouchers
  - cannot access `Users`, `Services`, `Reviews`, `Settings`
  - can view purchases but cannot update payment status
  - can perform voucher operational actions
- unauthorized / missing role
  - redirected away from admin or shown unauthorized state

### Direct URL and API checks
- Open restricted routes directly in the browser for each role
- Call `PATCH /api/orders/[id]/status` as staff and confirm `403`
- Call the same endpoint as manager/super admin and confirm success

### Data safety checks
- Confirm staff dashboard does not receive revenue-only data
- Confirm sidebar items match route permissions
- Confirm auth metadata and `public.admins.role` are synchronized after user create/update
- Re-run a Supabase audit query for role mismatches after rollout
