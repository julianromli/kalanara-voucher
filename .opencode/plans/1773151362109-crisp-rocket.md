# Admin Invite + Password Setup Plan

## Recommended Approach
Implement dual onboarding for new admin users, with `email invite` as the default and `manual password` as an optional alternative. Keep `public.admins` as the source of truth for role access. Use a public auth handoff under `/auth/*` so invite acceptance and password setup do not conflict with the existing `/admin/*` middleware.

## Scope
- Add onboarding mode selection to the admin user creation dialog.
- Support both:
  - `invite`: send Supabase invite email with a redirect into the app.
  - `manual`: create the auth user with a provided password.
- Add a public callback + set-password flow.
- After invite password setup succeeds, auto-enter the admin dashboard if the user still has a valid admin role.
- Add edit actions so super admin can update an existing admin's `name` and manually set a new `password` for emergency recovery.
- Allow self-edit for both `name` and `password` from the admin user management page.

## Edit Admin Flow
- Clicking the pencil button on `/admin/users` opens an `Edit Admin` dialog for that row.
- Dialog fields:
  - `Name` (required, editable)
  - `Email` (read-only)
  - `Password baru` (optional)
  - `Konfirmasi password` (optional)
- Empty password fields mean `name` only update.
- If a password is entered, confirmation must match and password must satisfy minimum length.
- Allow editing your own `name` and `password` from this dialog.
- Keep existing role-change protections unchanged.

## Implementation Notes
- Do not place invite or password-setup pages under `/admin/*`; keep them under `/auth/*` to avoid the current middleware redirect in `lib/supabase/middleware.ts`.
- Build invite `redirectTo` from `NEXT_PUBLIC_APP_URL`.
- Continue using `public.admins` as the authorization source; auth metadata remains best-effort only.
- No database migration is required unless invite lifecycle tracking is later needed.
- Preserve current permission checks: only users with `users.manage` can create admin accounts and perform edit actions.
- For edit actions, update the `admins` row first, then sync auth metadata/password so UI and RBAC data remain centered on `public.admins`.
- If auth sync fails after the DB update, treat the operation as failed in the UI with a clear error message and audit/log the mismatch for manual follow-up.

## Validation Rules
- `invite` mode is the default in the create dialog.
- `manual` mode requires non-empty password and confirm password.
- Prevent submit when password confirmation mismatches.
- Keep role selection unchanged from the current admin flow.
- Edit dialog requires non-empty trimmed `name`.
- Edit dialog password is optional, but when provided must be confirmed and meet minimum length.

## Failure Handling
- If auth user creation/invite succeeds but `admins` insert fails, delete the created auth user.
- Handle duplicate email/admin cases with clear UI errors.
- Handle expired, reused, or invalid invite links on `/auth/set-password`.
- If a signed-in invited user no longer has a valid `admins` row, sign them out and send them to `/admin/login?error=no_admin_access`.
- Never log or expose manual passwords.
- If edit target is missing, return a clear `admin tidak ditemukan` style error.
- If auth password or metadata sync fails during edit, surface a clear failure message and keep the operation visibly failed in the UI.
